# Agent Note: 先拆页面，再用 Betterer 基线锁住文件与函数的体量

Status: implemented

## Problem

`LingualabPage.tsx` 长到了 1662 行：一个组件函数约 1180 行代码，圈复杂度 130，有 29 个
`useCallback`、16 个 `useState`、12 个 `useEffect`。九月以来每个功能都动过它，这不是马虎：页面
是互相不许导入的几个 feature 碰面的地方，每新增一项能力，接线就加在这里。结果是一个没人能装进
脑子里的文件。键盘处理是 28 个分支，紧挨着它要改的状态，所以加一个键就得把整段读完；几个 effect
的先后顺序要紧，却只写在代码行的次序里，别处没有记录；而整页不挂载起来，里面什么也测不了。

整个仓库也是同一种形状，只是小一些。照 fsd-react 数的那三条规则，源码里约有 70 处过线（函数超过
80 行、复杂度超过 15，或文件超过 250 行），页面是其中最重的一处。让构建在这全部处失败的规则，当天
就会被关掉。

## Decision

**拆页面，行为不变。** 页面保留自己的状态、feature 之间的接线和两个视图的组合，其余都搬了出去，
一个关注点一个文件，凡是逻辑都带测试：

- 一个键意味着什么是纯函数（`keymap.ts`），每个动作做什么是一张表（`key-actions.ts`），事件处理、
  耳机的按键、亮起的键帽合成一个 hook（`useKeyboard.ts`）；耳机问的是同一份 keymap，只是把只关乎
  焦点的标志关掉，不再保留一份手抄的方向键逻辑；
- 复习、听到哪里与书签、打开、重放收藏的句子、舞台上这一句的笔记、时间条、放什么与对它说什么，
  各是一个 hook，规则放在旁边的纯模块里；
- 两个视图是组件（`HomeView`，以及带顶栏和两个面板的 `PracticeView`），自己都没有状态。

页面从 1662 行变成 599 行。首页、练习页的两个栏、每个浮层和抽屉、带视频的一段、结束卡片，一共十二种
状态，拆之前与拆之后各渲染成字符串，逐字节相同。

**用 Betterer 基线锁住体量。** `npm run betterer:ci` 对 `src/` 跑 ESLint 的 `complexity`（15）、
`max-lines`（250）与 `max-lines-per-function`（80），测试与 `testing/` 里的辅助不算，对照
`.betterer.results`，那里记着今天已经过线的地方。阈值是 fsd-react 在用的，所以同样的数字在两个项目里
意思一样。它跑在 `npm run verify` 的全档里（约二十秒），不进提交前钩子。

有一处和 fsd-react 的配置不同，而它正是让这道门成为棘轮的地方。`@betterer/eslint` 靠「位置加那一处
源码的哈希」认同一个问题，实测有两个后果：已超标的函数写长一点，它认为还是「同一个问题」，所以
函数可以变大而门毫无察觉；`max-lines` 又被记在「第 251 行到文件末尾」上，于是超过 250 行的文件里，
凡是改变长度的编辑（给 `locale.ts` 多加一条文案，给样式多加一条规则）都被读成「旧问题修好了、新问题
出现了」而失败。这里照 `@betterer/eslint` 的写法自己包了一层 ESLint，换了问题的记法，让它与大小成比例、
与位置无关：

- 超过 250 行的文件，每超出（不足 10 行按 10 行算）一档记一个问题，共 `ceil((行数 - 250) / 10)` 个；
- 超过 80 行的函数记 `ceil((行数 - 80) / 10)` 个；复杂度超过 15 的函数，每超出一点记一个；
- 每个问题都记在文件开头（第 0 行），身份是规则、函数名（匿名函数用它那一行的文本）、同名里的第几个、
  第几档，从不含行号；文件自己的哈希也不记，只记一个随路径变的替身。

于是结果文件里没有位置，也没有无关编辑能挪动的哈希。门的行为是实测出来的，办法是改代码再跑
`betterer:ci`：

- 函数或文件长过它当前的 10 行一档，多出一个问题，失败（「变差了」）。档内通过：这 10 行就是松动，
  结果文件也不变。复杂度没有松动，一点就是一个问题。
- 新写一个超过 80 行的函数、一个复杂度超过 15 的函数、一个超过 250 行的文件，都会失败，往已经在基线里
  的文件中加一个新的超标函数也一样。
- 函数或文件缩过一档，会报「变好了」并以退出码 7 失败，直到 `npm run betterer` 重写结果并把改动提交；
  此后它再也回不来。`npm run betterer` 从不记录更差的结果（退出码 7，文件不动）；只有 `--update` 会，
  这里没有任何地方用它。
- 没有跨档的编辑既不失败，也不碰 `.betterer.results`：给 `locale.ts` 多加一条文案、给样式多加一条规则、
  在 `store.ts` 的复杂函数上面加几行，都以退出码 0 通过。多数功能都会动这些文件，每个 PR 都要求更新
  基线的门是活不下去的。
- 给基线里的函数改名，或改匿名函数的第一行，身份就变了，被读成修好一个、出现一个，会失败；拆分要在
  同一次改动里做。

给新工作的规矩一并立下：新逻辑进切片自己 `lib/` 里带测试的 hook 或纯函数，一个组件眼看要过 80
行就拆开，不往基线里加。页面在基线里，是因为组合这么多 feature 的页面本来就长；那记录的是现状，
不是给它留余地。

## Alternatives considered

- **三条规则直接做成 ESLint 报错。** 信号最干净，新项目会这么做。这里它会在约 70 处现存的地方
  同时失败，拆完之后的页面也在其中，而出路只有两条：先全部修掉（重写每个 widget，其中没有一个
  背着 bug），或者把规则关掉。棘轮让规则一直开着，旧债一次拆一处地还。
- **ESLint 警告。** 一直都在的警告，一周内就会被当成噪音。
- **原样使用 `@betterer/eslint` 的 `eslint()`。** fsd-react 跑的就是它，我们不用写代码。它是先试的，
  后来放下，原因有两重：它让已超标的函数或文件继续变大，而这正是棘轮要管的事（页面可能重新长回一千行），
  并且它对 `max-lines` 的记法让加一条 locale 文案也会挂门。
- **每超出十行记一个问题，是个折中。** 每行一个能精确挡住变大，但结果文件会和超标的代码一样长（这里
  是几千条，主要来自 `styles.ts` 和 `locale.ts`）；每个函数一个就是原来那道门。十行一档，条目约 870 条，
  又给诚实地修一个长函数留出了松动。
- **给这个仓库另定阈值。** 三个数字用 fsd-react 的，是有意的：同一个主人名下的几个项目用一套
  上限，在一个项目里学到的拆法能带到另一个项目。
- **把体量检查放进提交前钩子。** 在一个已经要跑一分多钟的钩子上再加约二十秒；CI 里的全档会在合并前
  抓住它，和 `lib/` 的检查一样。

## Consequences

下一个要动页面的功能，有地方放自己的逻辑，也有测试护着不该碰坏的邻居，键盘处理一屏就能读完。
这道门在全档里多一步，外加一个习惯：拆了大函数之后跑 `npm run betterer` 并提交
`.betterer.results`；它发生合并冲突时跑 `npx betterer merge`。

有一处限制是接受下来的。十行一档是松动，函数在门察觉之前还能多长最多九行，门守住的是档，不是行。
还有，拆分把页面的 effect 搬进了 hook，其中四个的相对顺序变了：给面板焦点和解锁录音播放的那三个，
现在排在位置记录那几个之后，而不是夹在它们中间；键帽的清理则排在视频提示的计时器之后。它们都不读
别人写的东西，而真正要紧的那个顺序（先重置播放器，再应用续听）保留了，并写在 `useResume.ts` 里。
