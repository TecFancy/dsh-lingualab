# Agent Note: 先拆页面，再用 Betterer 基线锁住文件与函数的体量

Status: implemented

## Problem

`LingualabPage.tsx` 长到了 1662 行：一个组件函数约 1180 行代码，圈复杂度 130，有 29 个
`useCallback`、16 个 `useState`、12 个 `useEffect`。九月以来每个功能都动过它，这不是马虎：页面
是互相不许导入的几个 feature 碰面的地方，每新增一项能力，接线就加在这里。结果是一个没人能装进
脑子里的文件。键盘处理是 28 个分支，紧挨着它要改的状态，所以加一个键就得把整段读完；几个 effect
的先后顺序要紧，却只写在代码行的次序里，别处没有记录；而整页不挂载起来，里面什么也测不了。

整个仓库也是同一种形状，只是小一些。照 fsd-react 数的那三条规则，源码里约有 70 处过线（函数超过
80 行、复杂度超过 15，或文件超过 250 行），页面是其中最重的一处。让构建在这全部处失败的规则，当天
就会被关掉。

## Decision

**拆页面，行为不变。** 页面保留自己的状态、feature 之间的接线和两个视图的组合，其余都搬了出去，
一个关注点一个文件，凡是逻辑都带测试：

- 一个键意味着什么是纯函数（`keymap.ts`），每个动作做什么是一张表（`key-actions.ts`），事件处理、
  耳机的按键、亮起的键帽合成一个 hook（`useKeyboard.ts`）；耳机问的是同一份 keymap，只是把只关乎
  焦点的标志关掉，不再保留一份手抄的方向键逻辑；
- 复习、听到哪里与书签、打开、重放收藏的句子、舞台上这一句的笔记、时间条、放什么与对它说什么，
  各是一个 hook，规则放在旁边的纯模块里；
- 两个视图是组件（`HomeView`，以及带顶栏和两个面板的 `PracticeView`），自己都没有状态。

页面从 1662 行变成 599 行。首页、练习页的两个栏、每个浮层和抽屉、带视频的一段、结束卡片，一共十二种
状态，拆之前与拆之后各渲染成字符串，逐字节相同。

**用 Betterer 基线锁住体量。** `npm run betterer:ci` 对 `src/` 跑 ESLint 的 `complexity`（15）、
`max-lines`（250）与 `max-lines-per-function`（80），测试与 `testing/` 里的辅助不算，对照
`.betterer.results`，那里记着今天已经过线的地方。阈值和机制都是 fsd-react 在用的，所以同样的数字
在两个项目里意思一样。它跑在 `npm run verify` 的全档里（约二十秒），不进提交前钩子。

有一处和 fsd-react 的配置不同。`@betterer/eslint` 把 `max-lines` 记在「第 251 行到文件末尾」那一段
上，并拿这段文本做哈希，所以在超过 250 行的文件里，凡是改变长度的编辑（给 `locale.ts` 多加一条文案，
给样式多加一条规则）都会被读成「旧问题修好了、新问题出现了」，门就挂。这里的做法是照
`@betterer/eslint` 的写法自己包一层 ESLint，把这一条规则记在文件开头、哈希固定，于是一个仍然过线
的文件，怎么改都还是同一个问题。

门的行为是实测出来的，办法是改代码再跑 `betterer:ci`：

- 新写一个超过 80 行的函数、一个复杂度超过 15 的函数、一个超过 250 行的文件，都会失败（「变差
  了」），往已经在基线里的文件中加一个新的超标函数也一样。
- 已超标的函数多写一行**不会**被抓住：Betterer 靠位置和那里的源码文本认同一个问题，不看消息里
  的数字，所以它还是同一个问题。它会在 `.betterer.results` 里表现为 `(91)` 变成 `(92)`。
- 改过基线里的任何文件，`betterer:ci` 都会以「结果没变，但代码变了」失败，直到 `npm run betterer`
  重写这份文件并把改动提交。这是 Betterer 的工作方式（结果的键里有文件哈希），也正是它把
  `(91)` 变 `(92)` 摆到评审者面前的方式。
- 把一个函数拆到阈值以内，会报「变好了」，同样失败，直到 `npm run betterer` 收紧基线；此后它再也
  回不来。
- `npm run betterer` 从不记录更差的结果（退出码 7，文件不动）；只有 `--update` 会，这里没有任何
  地方用它。

给新工作的规矩一并立下：新逻辑进切片自己 `lib/` 里带测试的 hook 或纯函数，一个组件眼看要过 80
行就拆开，不往基线里加。页面在基线里，是因为组合这么多 feature 的页面本来就长；那记录的是现状，
不是给它留余地。

## Alternatives considered

- **三条规则直接做成 ESLint 报错。** 信号最干净，新项目会这么做。这里它会在约 70 处现存的地方
  同时失败，拆完之后的页面也在其中，而出路只有两条：先全部修掉（重写每个 widget，其中没有一个
  背着 bug），或者把规则关掉。棘轮让规则一直开着，旧债一次拆一处地还。
- **ESLint 警告。** 一直都在的警告，一周内就会被当成噪音。
- **原样使用 `@betterer/eslint` 的 `eslint()`。** fsd-react 跑的就是它，我们不用写代码。它是先
  试的，后来因为上面说的 `max-lines` 行为放下了：用它的话，加一条 locale 文案就要更新基线，或者去
  拆一个本来是数据而不是设计的词典。
- **连变大也能抓住的更严的棘轮。** 做得到，办法是写一个自定义测试，每超出十行报一个问题，这样把
  函数写到下一档就是新问题，写短一点就修好一个问题。没有做：结果文件要多出几百行，`locale.ts`
  和样式这类数据文件得排除出去，而相对于评审者在 diff 里看到 `(91)` 变成 `(92)`，在这么大的仓库
  里收益不大。它可以只改 `.betterer.ts` 加上，别处都不用动。
- **给这个仓库另定阈值。** 三个数字用 fsd-react 的，是有意的：同一个主人名下的几个项目用一套
  上限，在一个项目里学到的拆法能带到另一个项目。
- **把体量检查放进提交前钩子。** 在一个已经要跑一分多钟的钩子上再加约二十秒；CI 里的全档会在合并前
  抓住它，和 `lib/` 的检查一样。

## Consequences

下一个要动页面的功能，有地方放自己的逻辑，也有测试护着不该碰坏的邻居，键盘处理一屏就能读完。
这道门在全档里多一步，外加一个习惯：拆了大函数之后跑 `npm run betterer` 并提交
`.betterer.results`；它发生合并冲突时跑 `npx betterer merge`。

有两处限制是接受下来的。门拦不住已超标的函数继续变大，只拦它再多一个同伴（上面那个更严的棘轮
才拦得住）。还有，拆分把页面的 effect 搬进了 hook，其中四个的相对顺序变了：给面板焦点和解锁录音
播放的那三个，现在排在位置记录那几个之后，而不是夹在它们中间；键帽的清理则排在视频提示的计时器
之后。它们都不读别人写的东西，而真正要紧的那个顺序（先重置播放器，再应用续听）保留了，并写在
`useResume.ts` 里。
