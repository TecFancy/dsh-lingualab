# Agent Note: 先拆页面，再用 Betterer 基线锁住文件与函数的体量

Status: implemented

## Problem

`LingualabPage.tsx` 长到了 1662 行：一个组件函数约 1180 行代码，圈复杂度 130，有 29 个
`useCallback`、16 个 `useState`、12 个 `useEffect`。九月以来每个功能都改过它，这不是因为马虎：
几个 feature 之间不许互相导入，只能在页面里组合，所以每新增一项能力，接线就加在这里。结果是一个没人能完整记在
脑子里的文件：

- 键盘处理有 28 个分支，紧挨着它要改的状态，所以加一个键就得把整段读完；
- 几个 effect 的先后顺序很要紧，却只体现在代码行的次序里，别处没有记录；
- 不把整页挂载起来，里面什么也测不了。

整个仓库也有同样的问题，只是程度轻一些。按 fsd-react 统计的那三条规则，源码里约有 70 处超标（函数超过
80 行、复杂度超过 15，或文件超过 250 行），页面是其中最严重的一处。如果一条规则让构建在所有这些地方都失败，当天
就会被关掉。

## Decision

**拆页面，行为不变。** 页面只保留自己的状态、feature 之间的接线和两个视图的组合，其余都搬了出去，
一个关注点一个文件，凡是逻辑都带测试：

- 一个键表示什么由纯函数决定（`keymap.ts`），每个动作做什么是一张表（`key-actions.ts`），事件处理、
  耳机按键、点亮键帽合在一个 hook 里（`useKeyboard.ts`）；耳机查询的是同一份 keymap，只是把只和
  焦点有关的标志关掉，不再另外手抄一份方向键逻辑；
- 复习、听到哪里与书签、打开、重放收藏的句子、舞台上这一句的笔记、调整时间的横栏、播放什么以及针对它显示什么提示，
  各是一个 hook，规则放在旁边的纯模块里；
- 两个视图是组件（`HomeView`，以及带顶栏和两个面板的 `PracticeView`），自身都没有状态。

页面从 1662 行变成 599 行。首页、练习页的两种栏宽、每个浮层和抽屉、带视频的一段、结束卡片，一共十二种
状态，拆之前与拆之后各渲染成字符串，逐字节相同。

**用 Betterer 基线锁住体量。** `npm run betterer:ci` 对 `src/` 执行 ESLint 的 `complexity`（15）、
`max-lines`（250）与 `max-lines-per-function`（80），测试和 `testing/` 里的辅助代码不算，结果与
`.betterer.results` 对照，那里记着目前已经超标的地方。阈值和 fsd-react 用的一样，所以同样的数字在两个项目里
含义相同。它在 `npm run verify` 的全档里执行（约二十秒），不进提交前钩子。

有一处和 fsd-react 的配置不同，正是这一处让体量门只许变好、不许变差（像棘轮一样）。`@betterer/eslint` 靠「位置加上那一处
源码的哈希」来识别同一个问题，实测有两个后果：

- 已经超标的函数再写长一点，它仍认为是「同一个问题」，所以函数可以继续变大而检查毫无察觉；
- `max-lines` 被记在「第 251 行到文件末尾」上，于是在超过 250 行的文件里，凡是改变文件长度的编辑
  （给 `locale.ts` 多加一条文案，给样式多加一条规则）都被认为是「旧问题修好了、新问题出现了」，检查因此失败。

这里照 `@betterer/eslint` 的写法自己包了一层 ESLint，换了一种记录问题的方式，让问题数与超标的程度成比例、与位置无关：

- 超过 250 行的文件，每超出 10 行（不足 10 行按 10 行算）记一个问题，共 `ceil((行数 - 250) / 10)` 个；
- 超过 80 行的函数记 `ceil((行数 - 80) / 10)` 个；复杂度超过 15 的函数，每超出一点记一个；
- 每个问题都记在文件开头（第 0 行），用这些来识别：规则、函数名（匿名函数用它那一行的文本）、同名函数里的第几个、
  第几档，从不包含行号；文件自己的哈希也不记，只记一个随路径变化的替代值。

于是结果文件里没有位置，也没有会被无关编辑改变的哈希。检查的行为是实测出来的，办法是改代码再执行
`betterer:ci`：

- 函数或文件的长度超出当前所在的 10 行一档时，多出一个问题，检查失败（「变差了」）。在档内则通过：这 10 行就是余量，
  结果文件也不变。复杂度没有余量，超出一点就是一个问题。
- 新写一个超过 80 行的函数、一个复杂度超过 15 的函数、一个超过 250 行的文件，都会失败；往已经在基线里
  的文件中加一个新的超标函数也一样。
- 函数或文件缩短到低一档时，会报「变好了」并以退出码 7 失败，直到执行 `npm run betterer` 重写结果并把改动提交；
  此后它就再也不能变回去。`npm run betterer` 从不记录更差的结果（以退出码 7 退出，文件不动）；只有 `--update` 会记录，
  这里没有任何地方用它。
- 没有跨档的编辑既不会失败，也不会改动 `.betterer.results`：给 `locale.ts` 多加一条文案、给样式多加一条规则、
  在 `store.ts` 的复杂函数上方加几行，都以退出码 0 通过。多数功能都会改这些文件，如果每个 PR 都要求更新
  基线，这道检查坚持不了多久就会被关掉。
- 给基线里的函数改名，或修改匿名函数的第一行，它的标识就变了，会被认为是修好一个、出现一个，检查失败；拆分要在
  同一次改动里完成。

同时给新工作立下规矩：新逻辑放进切片自己 `lib/` 里带测试的 hook 或纯函数，一个组件快要超过 80
行就拆开，不往基线里加。页面之所以在基线里，是因为组合这么多 feature 的页面本来就长；基线记录的是现状，
不是给它留出增长的空间。

## Alternatives considered

- **三条规则直接做成 ESLint 报错。** 信号最清楚，新项目会这么做。但在这里，它会在约 70 处现有代码上
  同时失败，拆完之后的页面也在其中，出路只有两条：先全部修掉（等于重写每个 widget，而其中没有一个
  存在 bug），或者把规则关掉。只许变好的基线能让规则一直开着，旧债每次拆一处慢慢还。
- **ESLint 警告。** 一直都在的警告，不出一周就会被当成噪音。
- **原样使用 `@betterer/eslint` 的 `eslint()`。** fsd-react 用的就是它，不需要自己写代码。它是先试过的，
  后来放弃了，原因有两个：它允许已经超标的函数或文件继续变大，而这正是要管住的事（页面可能重新长回一千行）；
  它对 `max-lines` 的记录方式又会让加一条 locale 文案也导致检查失败。
- **每超出 10 行记一个问题，是个折中。** 每行记一个能精确地挡住变大，但结果文件会和超标部分的代码一样长（这里
  是几千条，主要来自 `styles.ts` 和 `locale.ts`）；每个函数只记一个，就是原来那种检查。10 行一档，条目约 870 条，
  也给认真修一个长函数的人留出了余量。
- **给这个仓库另定阈值。** 三个数字沿用 fsd-react 的，是有意的：同一个主人名下的几个项目用同一套
  上限，在一个项目里学到的拆法能用到另一个项目上。
- **把体量检查放进提交前钩子。** 这会在一个已经要执行一分多钟的钩子上再加约二十秒；CI 里的全档会在合并前
  发现问题，和 `lib/` 的检查一样。

## Consequences

下一个要改页面的功能，有地方放自己的逻辑，也有测试保护不该被改坏的相邻代码，键盘处理一屏就能读完。
这道检查让全档多了一步，另外多了一个习惯：拆了大函数之后执行 `npm run betterer` 并提交
`.betterer.results`；`.betterer.results` 发生合并冲突时执行 `npx betterer merge`。

有两处限制是接受下来的：

- 10 行一档是余量，函数在检查察觉之前最多还能多长九行，检查守住的是档，不是每一行。
- 拆分把页面的 effect 搬进了 hook，其中四个的相对顺序变了：给面板焦点和解锁录音播放的那三个，
  现在排在位置记录那几个之后，而不是夹在它们中间；键帽的清理则排在视频提示的计时器之后。它们都不读取
  别的 effect 写入的东西，而真正要紧的那个顺序（先重置播放器，再应用续听）保留了下来，并写在 `useResume.ts` 里。
