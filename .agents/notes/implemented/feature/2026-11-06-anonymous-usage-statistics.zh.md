# Agent Note: 匿名上报不带内容，一个配置项就能关掉

Status: implemented

## Problem

这个插件以前说不出自己有没有被装过、被用过，也说不出某次安装跑的是哪个版本。面板关于自己知道的一切，
都是在跑它的那台机器上读的：首页页脚报出构建，发版检查比发布标签，库扫描数剧集。这些没有一样能传到维护
插件的人那里，所以「有多少台机器、分别是哪个版本」完全没有答案。看上去最快的几种办法，账号、托管看板、
第三方统计 SDK，恰好都是这个仓库在别处一直躲着的那类依赖。

问题是有意收窄到两个数字的：有多少次安装真的在用这个插件，每一个跑的是哪个版本。再有意思一点的信息，
比如练了哪几集、用了哪些功能、用了多久，都要带上用户机器上的内容或行为，而内容是不能离开那台机器的。

## Decision

服务端向 `https://t.hi-ruofei.com/v1/ping` 发一次 `POST`，一个进程里最多每 24 小时一次，而且只在
`guarded()` 放行了一个请求之后才发：启动了却没人用的进程什么都不发。请求体就是契约里的 v1 载荷：载荷版本、
从 `package.json` 读到的包名、加载时读的版本号、随机的安装 id、Node 主版本号、`os`、`arch`，加上这个包
上报的两个指标，媒体库根目录的剧集文件夹分成四档，以及能不能找到 `ffmpeg`。`locale` 不发，因为这个插件
没有现成的宿主 locale 服务可读，契约说拿不到就整条省略，不要猜。

这个请求是一条单向的事实，所以发出去就不再管。它限时五秒，不重试、不写日志，所有失败都落在模块自己的
`catch` 里；启动它的那个请求早就被放行，不管上报怎么样都会正常作答。guard 是把这个钩子当参数收下的，
不是自己 import 网络：`admitRequest` 因此仍然是一个纯判断，上报在它之外。

id 是 `crypto.randomUUID()` 生成的 UUID v4，在配置里隐藏且 volatile。它在第一个被放行的请求上生成，
然后通过设置服务写回这个插件自己的 profile 条目，和 `openState`、`libraryRoot` 一样；没有我们自己的状态
文件。写回是要等的，而且每次上报都会重试到写成为止：发出去就不管的写法和写失败分不出来，那样 id 每次
重启都是新的，数出来的是安装次数而不是机器数。一直写不成功也不影响这次上报。

开关是普通的、可见的 `telemetry` 布尔项，默认开。关掉就等于不生成 id、不列媒体库、不发请求：模块在动手
之前先看它。插件里没有别的地方读它，关掉之后面板没有任何变化。

## Alternatives considered

**机器指纹。** 对主机名、MAC 地址或机器 id 做哈希，可以不存东西就认出一台机器，问题也在这里：它是稳定的、
由硬件推出来的，用户没法重置。配置里的随机 id 可以手动删掉，不指向任何东西，也不会把两次安装联起来。

**第三方 SDK。** 统计或崩溃 SDK 能回答得多得多，代价是一个依赖、一个不归我们管的出网域名、它的数据保留
策略，以及它对「事件」的定义。整份上报就是一个小请求，SDK 会比功能本身还大。

**在面板前面加登录。** 用账号来统计最准确，也会让这个面板需要账号。它是一个打开机器上文件夹的学习工具，
登录就是换个名字的付费墙，契约也明确不做。

**完全不发，或者默认关、愿意的人自己开。** 默认关的上报只能问到读过 README 的那批人，答案是有偏的样本。
带上内容的上报很准确，却破了唯一真正要紧的那条规矩。中间那条线是一个很小、固定的请求体，默认开着、
可见、可关，而且两份 README 说清楚报什么、绝不报什么，以及关掉它的确切配置键。

**定时器。** 每天一次的定时器会让一个没人用的安装也上报。上报做成懒的：触发点是放行过的请求，那是插件
被用过唯一诚实的证据。

## Consequences

维护插件从此有一个数字可看，而不是靠猜；代价是一个在用的安装每天发一个出网请求，去一台不属于本机的
主机。网络挡掉这个端点时，不会有重试，插件也不会抱怨；面板表现得像没有这个功能。

端点现在还没建。在它建好之前，每次上报都静默失败，这是契约预期中的行为；以后成功了，这一侧也没有区别。

载荷除了 `v` 没有别的版本协商，所以将来改键集合就是 `v2`，接收侧要同时认两种。测试把确切的键集合钉住，
原因就在这里。
