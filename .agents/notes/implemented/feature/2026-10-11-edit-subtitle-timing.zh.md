# Agent Note: 调整一句字幕的时间

Status: implemented

## Problem

网上找来的字幕，时间常常差一点：一句比人声早开始一拍，或者拖到下一句的第一个词。这个页面以循环一句为核心，
所以这不是小瑕疵：

- 每循环一遍，都会切掉半个词，或者多放出下一句的一小段。
- 跟读停在错误的位置。
- 用户没有办法修正，只能用别的工具打开文件、猜毫秒数、再重新加载。

问题出在个别句子上，不是整个文件：用户看到某一句不对，前后的句子都没问题。整体偏移解决不了这种情况。

## Decision

**舞台上那一句的开头和结尾可以调整，改动写回字幕文件。** 这样别的播放器和 agent 读到的也是改好的文件，
页面也不会多出第二个时间来源，需要和文件核对。

**编辑器是舞台下面的一条横栏，从时间范围打开。** 舞台上已经显示这一句的时间范围（`00:18 – 00:22`）。点它、按 `T`，
或者在「更多」里选「调整这一句的时间」，都会打开横栏，显示精确到毫秒的开头和结尾（`00:18.250`），各带微调按钮。
横栏打开期间这一句一直循环，所以每次改动在下一遍就能听到。横栏打开时由它处理键盘：

| 键 | 作用 |
|---|---|
| `Tab` | 在开头和结尾之间切换 |
| `←` `→` | 把当前这一端微调 50 毫秒 |
| `Shift` + `←` `→` | 微调 250 毫秒 |
| `I` / `O` | 把开头 / 结尾设到当前播放位置，和剪辑软件的入点、出点一样 |
| `Space` | 播放或暂停 |
| `↑` / `↓` | 切到上一句 / 下一句，改过的先保存（后来加的，见[切换那篇 note](2026-10-12-step-to-neighbour-while-retiming.zh.md)） |
| `Enter` | 保存 |
| `Esc` | 不保存，关掉 |

没有波形（见
[2026-10-08-v1-without-waveform](../../implemented/simplification/2026-10-08-v1-without-waveform.zh.md)），
只能靠耳朵：有了循环，再边听边按 `I` / `O`，才能实际定准一句的边界。

边界碰到相邻的句子时会推着它走，而不是停住：

- 很多文件的句子是首尾相接切分的，一句的开头就是上一句的结尾。人声提前开始的那一句，只有把开头挪进上一句才改得过来。
- 这时上一句的结尾跟着挪；结尾挪过下一句的开头时，下一句的开头也跟着挪。横栏在按键说明下面写明这一点，保存时两句一起写入。
- 推到相邻那句只剩 0.2 秒时停住，每一句也至少保留 0.2 秒。
- 原本就有重叠的文件，在边界推进重叠区之前保留原有的重叠。

**保存时只改时间那一行，其余都不动。**

- 服务端（host）在文件的字节里找到这一句的时间行，只替换其中的时间。序号、文本、样式标签、空行、换行符和编码都不变。
- GBK 和 GB18030 的文件也靠这种做法原样保留：时间是 ASCII 字符，在这两种编码里与 UTF-8 逐字节相同，
  所以周围的字节不需要解码再编码（Node 没有 GBK 编码器）。
- 带 BOM 的 UTF-16 文件，借助 Node 自带的 UTF-16 支持重写。
- 新的时间沿用那一行原来的格式：毫秒前面用 `,` 还是 `.`，小时写几位，都和原来一样。

**按文件里写的内容定位一句，页面内容过期就拒绝。**

- 请求写明文件、这一句原来的开始和结束（毫秒），以及它在时间范围完全相同的几句里排第几（几乎总是第一句）。
- 请求还带着页面解析时那份字节的哈希。如果文件之后变过，服务端回 `409` 并说明原因，页面重新加载字幕，
  而不是覆盖一次它没见过的修改。
- 写入时先写临时文件，再 rename 到位，和进度文件一样，因为这里本来就是要整份替换文件。
- 第一次写某个文件之前，服务端把原文件复制一份到旁边的 `<name>.bak`，只复制一次，以后也不覆盖。

**中文在另一个文件里时，两个文件一起改。** 页面按开始时间把中文轨合并进英文轨，容差 0.6 秒。只改英文的开头，
可能导致配对失败，中文那一行就丢了。所以中文来自单独的文件时，与这一句配对的中文句会在那个文件里做同样的改动，
放在同一个请求里。两种语言在同一个文件里的双语字幕，就是一个文件、一处改动。

**LRC 只有开始时间。** 一行在下一行开始时结束，所以只能改开头，结尾显示为下一行的开头，只读。

**只有媒体库里的文件能改。** 文件剧集的字幕放在用户自己选的位置，不在这个插件会写入的文件夹里。
对这些字幕横栏也能打开，但会说明为什么不能保存。文件夹剧集和库根目录下散放的文件都算在媒体库里。

**收藏跟着句子走。** 收藏按整秒和文本匹配。开头跨过一个整秒时，页面会在字幕保存成功之后改写笔记里那条收藏的 `at`，
星标就不会丢。

**服务端多一条写入路由。**

```ts
// POST /lingualab/subtitle-timing
export interface TimingEdit {
  /** The subtitle file's name inside the episode folder. */
  readonly file: string
  /** The cue as the file has it now, in milliseconds. */
  readonly from: { readonly start: number; readonly end: number; readonly occurrence: number }
  /** The new range, in milliseconds. For LRC only `start` is used. */
  readonly to: { readonly start: number; readonly end: number }
  /** SHA-256 of the bytes the page parsed, hex. */
  readonly expect: string
}

export interface TimingWriteRequest {
  readonly episode: string
  /** One edit, or two when the Chinese lives in its own file. */
  readonly edits: readonly TimingEdit[]
}
```

两处改动都检查通过后才写入文件，所以不会出现同一句在一个文件里挪了、在另一个文件里没挪的情况。

**不在这次范围内：**

- 整个文件的偏移和两点线性校正（用户遇到的问题是逐句的）。
- 波形。
- 拆分或合并句子。
- 编辑文本。
- `.bak` 副本和「把旧时间再存一次」之外的撤销。

## Alternatives considered

- **把校正存在文件旁边，放进库根目录的一个隐藏 JSON，加载时套用。** 与字幕格式无关，可以撤回，素材目录也只保留原来的三处写入。
  但别的播放器和 agent 都看不到这些校正，而且文件一旦被替换，页面上的两个时间来源就会各不相同。
- **解析整个文件、修改、再序列化。** 代码更简单，但解析器会丢掉用不上的内容（序号、样式标签、解析不了的块），还会给句子排序，
  所以保存一次会把用户的文件改得远不止那一句，GBK 文件也会变成 UTF-8。
- **按解析后列表里的序号定位一句。** 解析器会排序、会丢块，页面里的序号不等于文件里的序号。
- **先做整个文件的偏移。** 这是字幕工具里最常见的修正，但不是这里说的问题，而且以后在同一条路由上很容易加上。

## Consequences

- 素材目录多了第四处写入：媒体库里的字幕文件和它们的 `.bak` 副本。`AGENTS.md` 和技能的约定 4 要把它列上。
- `T` 加入「更多」里的按键列表，「更多」里也多一项用来打开横栏；横栏自己的键（`I`、`O`、`Tab` 和方向键）写在横栏上，
  也只在横栏上生效。
- 句子类型要记录每一句的出处（文件、原来的时间范围、第几句，以及配对的中文句的这些信息）。解析器和合并步骤负责记下这些，
  返回给其他代码的内容不变。
- 新路由意味着 `dsh-plugin.naming.json` 和 README 的路由表都要改（`check-host.mjs` 拿记录和 `protocol.ts` 比对，
  不用另改），服务端也要重启。
- 这一项排在复习收藏
  （[2026-10-11-review-kept-sentences](2026-10-11-review-kept-sentences.zh.md)）之前，因为逐句循环的复习依赖句子的边界准确。
- 页面用自己实现的 SHA-256 计算哈希，不用 `crypto.subtle`：后者只在安全上下文里存在，从另一台机器用普通 HTTP
  打开 dsh web 时，编辑器就永远存不了。
- 每一端的可调范围以文件里相邻句子另一端的时间为界。播放切到别的句子（或循环某一句）时编辑结束，
  所以横栏不会去改一句没在播放的边界。
