# Agent Note: 在进度条上精细拖动

Status: implemented

## Problem

播放卡片里的进度条把整集压缩在几百个像素里。iPad 横屏时进度条约 546px 宽，一集一个半小时的录音，一个像素就接近十秒，
想落在某一句上要试好几次。按下之后、松手之前什么也看不到，所以每试一次都要跳转一次、再试听一次。

2026-10-21 提出的问题是：侧栏可以收起以后，用户怎么找到离舞台上那一句很远的句子。当时一起提了两个办法：在舞台上按住再拖，
目前仍是提案；在进度条上精细拖动，记在这篇里。两者中进度条的成本更低：它只改一个现有的控件，不和任何手势冲突。

## Decision

**按住滑块时，手指往上或往下离进度条越远，拖动速度就分档降低，和 iOS 的音乐 App 一样；滑块上方的标签显示滑块的位置。**

- **三档速度，每档相隔 44px。** 在进度条上和离它 44px 以内是全速，从 44px 起是半速，从 88px 起是四分之一。往上往下的距离都算：
  横屏时进度条离可见区域的底边只有约 120 到 140px（下面实测的布局里是 139px，算上宿主自己的边栏还会更少），
  进度条下方最多只放得下三档这样的距离。
- **换档时滑块不动。**
  - 水平移动按当前速度、相对于进入这一档时的位置计算；跨进新一档的那一下移动仍按旧速度算，
    然后新一档以滑块当时的位置为起点。
  - 全速时、还没换过档之前，滑块和以前一样正好在手指下面，所以普通的拖动和点击都和以前一样。
  - 回到全速时，滑块也不会跳回手指下面。
  - 慢档下手指越过进度条的任何一端以后，滑块仍会继续移动，直到走到头。
- **标签。**
  - 按住滑块时，滑块上方的标签显示当前速度（「全速」、「半速」、「四分之一」）、时间、句子序号（「第 646 句」）
    和那一句的内容，最多两行。
  - 标签最宽 240px，会向内平移，保证留在播放卡片以内，必要时盖住两边的时间；卡片比这还窄时，标签就缩到卡片的宽度。
  - 标签跟着滑块走，不跟着手指。
  - 鼠标悬停时仍然显示以前那个短一些的标签（时间和句子），位置现在按同一条规则摆放。
- **松手时只跳转一次**，跳到滑块所在的位置，和进度条一直以来的做法一样。键盘操作不受影响：进度条仍然不是 Tab 停靠点，
  方向键仍然按句子移动。
- **代码在哪里。**
  - 速度与位置的计算、标签的摆放，都是 `widgets/control-bar/lib/fine-scrub.ts` 里的纯函数，带测试。
  - 标签针对某个位置显示什么，在 `scrub-point.ts`。
  - 指针处理是 `useScrubGesture` 这个 hook，它把拖动状态同时存在 ref 和 state 里，这样两次渲染之间到达的几次移动能依次累加。
  - 手指离开进度条时页面不会滚动、也不会按到下面的按钮，靠的是进度条原有的 `touch-action:none` 和指针捕获。
  - 进度条的样式从 `shared/lib/styles.ts` 移到了旁边的 `styles-scrub.ts`，在样式表里仍插在原来的位置，因为体量门在
    `styles.ts` 里已经没有余量；出于同样的原因，删掉了六个没有任何地方读取的文案键。

在 Chromium 里开启触屏模拟，把真实的控制栏和样式表放进练习栏的布局里，在 1180 乘 820、820 乘 1180 和 1180 乘 746 下测量：

- 手指移动 40px，滑块在全速时移动 40px，半速 20px，四分之一 10px；
- 换档时滑块的移动不到一个像素；
- 标签是 240 乘 72px，在进度条两端都留在卡片以内；
- 松手跳转到的时间就是标签上显示的时间。

## Alternatives considered

- **一律按相对位置拖动**，滑块永远不跳到按下的地方。这样在短的剧集上第一下触摸会显得没反应，而且会改变点击的效果；
  让全速保持按绝对位置定位，两者都能保持原样。
- **更多档位（从 132px 起是八分之一）。** 设计草图上只有进度条上方放得下这一档。只在一个方向上存在的档位很难学会，
  所以速度最低到四分之一。
- **按手指移动的快慢决定速度**，有些视频播放器是这样做的。这种速度在起作用之前看不出来，标签只能事后报告；而离进度条的距离看得见，
  也可以重复。
- **松手时吸附到句子开头。** 这里没有做：进度条一直是落在那个点上，再由播放器找到包含它的那一句，而标签已经显示了那一句。
