# Agent Note: 从用户自己电脑上的文件播放画面

Status: implemented

## Problem

在远程的 dsh 上，只有画面真正吃线路：字幕、笔记和进度只有几 KB，隐藏画面时放的是音频文件（一集 55 MB），
可显示画面时，准备好的视频要以约 5.5 Mbps 串流，而线路实测只有约 8.5 Mbps。同一天提出的流畅版能把它降到约
1.9 Mbps，代价是服务器要转码，画面也变小。

用户面前的电脑上往往就有同一个视频：剧集本来就是从那里导入的。从那里播放，画面完全不用走线路，跳转是磁盘的速度，
画质也是完整的。2026-10-13 提出的问题是：页面能不能播放这样的文件，又不把它放进媒体库。

在本地的 dsh 上这不改变什么：服务器就是这台电脑，本来就从磁盘读文件。收益在远程的 dsh 上。

## Decision

**视频舞台上加「用本地文件播放」：用户从自己的磁盘选这一集的视频，页面就用它代替服务器上的那份播放这一段，
不上传。**

- **什么都不离开浏览器。** 文件用文件选择框打开（或者拖到舞台上），通过对象 URL（`URL.createObjectURL`）播放。
  它不上传、不导入，也不写到任何地方；host 完全不知道它。把视频拖到舞台上是「放这个」，拖到首页仍然是「导入」，
  和现在一样。
- **它并入那一条时间线。** 本地文件经 `playSource` 成为媒体元素的来源，优先于服务器上的视频，会话不变，
  所以位置、循环、语速、字幕、收藏的句子、复习和五步法都和播放服务器上的视频时一样。隐藏画面仍然放音频文件；
  有本地文件时这不省什么，但规则只有一条。
- **必须是同一个视频。** 本地文件的时长和服务器上那份视频的时长比较（状态路由已经报告了它），那份没探测过就和音频文件的时长比较。
  相差一秒以内就当作同一个文件，服务器视频与音频之间已有的时长检查照样适用。时长不同时，显示现有的「字幕可能对不上」提示并给出差值，但照样播放，
  因为同一集的另一个剪辑版本仍然值得看。
- **必须是浏览器能放的文件。** 浏览器里没有 `ffmpeg`，所以到处都能放的格式是 `mp4`（H.264 加 AAC）。浏览器解不开的文件，
  经现有的「解不开」路径退回服务器上的来源，并提示改用 `mp4`。源 `mkv` 在 Chromium 里可能画面能放而声音不能放（DTS、AC-3），
  页面只事先提示这一点（见 Settled details）。
- **它在本次页面会话里有效，浏览器允许的话更久。** 对象 URL 随页面消失。支持 File System Access API 的地方
  （HTTPS 上的 Chromium，线上站点正是如此），文件句柄按段存进 IndexedDB，再次打开这一段时只问一次能否读取，
  不必重新选文件。其余情况用户再选一次。这些都不发给 host，所以和设置一样按设备保存。
- **一眼看得出来。** 舞台给本地画面加上「本地文件」标签，并提供停用它的办法，用户不会搞不清正在放哪个文件。

## Alternatives considered

- **把文件上传进媒体库。** 那就是现有的导入。上传要花一次，之后每次还要串流，而串流正是要解决的问题。
- **本地画面静音播放，声音用服务器上的音频。** 能应付声音是 DTS 的源文件，但这是两个媒体元素保持同步，视频那篇 note 已经否决了：
  每次跳转、改语速和循环都要做两遍，两者之间还会漂移。
- **把服务器上的视频一次性下载到浏览器存储（OPFS），之后从那里播放。** 不需要本地副本，但 941 MB 以 1 MB/s 下载约 15 分钟，
  浏览器对这么大的存储有上限，也可能清掉，而且 v0.9.3 的缓存校验头已经让 HTTP 缓存能留多少留多少。如果没有本地副本的用户有需要，
  这仍是一个选项。
- **并入流畅版那篇 note。** 两者回应的是同一个抱怨，但没有共用的代码：流畅版是 host 上改写文件的任务，这个是只在客户端的来源。
  分开写，各自可以单独实现或放弃，而且两者能叠加：有文件的用户在本地放，没有的用户用流畅版。

## Settled details

提出时还有两个开放问题，2026-10-13 动手之前定下了：

- **浏览器放不了的格式，只提示，不检测。** 选择处写明：`mp4`（H.264 加 AAC）到处都能放，`mkv` 常常没有声音，关于声音不再做别的。
  检测音轨缺失（非标准的 `webkitAudioDecodedByteCount`）或者读容器的轨道列表，是为一个用户换个 `mp4` 一分钟就能解决的情况写代码。
  浏览器完全解不开的文件，则退回服务器上的来源，提示改用 `mp4`，并且把这个文件忘掉，因为下次它同样解不开。
- **参照时长退回音频文件。** 先和服务器上那份视频探测到的时长比。host 从没探测过（视频从没准备过）时，由这一段的音频文件顶上，
  因为字幕本来就是对着它打的时间，所以任何有视频文件的段都能用本地画面，不管准备过没有。两个时长都不知道时，照样播放，不给提示。

动手时又定了这些：

- **本地文件排在服务器视频的所有状态之前**，包括正在跑的任务和失败的任务，只要这一段有视频文件就提供它：画面一角的小按钮，
  以及每张卡片最后一行。隐藏画面时规则和服务器视频自己的一样：放音频文件，没有音频文件的段放本地文件，因为那是仅有的声音。
- **时长由一个用完即弃的元素读取**，不用页面唯一的那个媒体元素，所以那个元素只加载文件一次。读不出时长的容器（部分 `mkv`）
  不给提示，而不是给一个错的。
- **两个警告，一条规则。** 本地文件和参照相差一秒以内就是同一个文件，这时服务器视频对音频的长度警告照样适用。
  不同的文件则改为显示现有的警告，给出和参照的差值（本地文件更长时为正）。
- **只有浏览器有 `showOpenFilePicker` 时才记住选择。** 句柄按段存在 IndexedDB 里，只在这台设备上。再次打开这一段，
  给出带文件名的「继续用本地文件」，因为请求读取权限需要一次点击；「忘记」会删掉它，「停用」不会（停用不代表这个文件不好），文件已经不在的句柄说明之后丢弃。
  其他浏览器用普通的文件输入框，用户每次页面会话重新选一次。IndexedDB 的每次调用都允许失败，失败时什么也不记。
- **对象 URL 与文件使用的时间一样长。** 文件被替换或停用时、换段时（记住的句柄会把文件还给用户）、页面关闭时，都会撤销它。
- **本地文件播放时不弹「视频准备好了」。** 这条提示说的是服务器上的视频，而那时放的不是它。
- **视频拖到练习页的舞台上就是选择它，不会再触发别的事。** 只收视频文件，拖进来的其他东西会被忽略（浏览器也不会把它打开），
  而且这次拖放不会到达导入，导入仍然只在首页。
