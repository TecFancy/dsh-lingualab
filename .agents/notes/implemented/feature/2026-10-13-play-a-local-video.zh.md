# Agent Note: 从用户自己电脑上的文件播放画面

Status: implemented

## Problem

在远程的 dsh 上，真正占用网络的只有画面：

- 字幕、笔记和进度只有几 KB。
- 隐藏画面时播放的是音频文件，一集 55 MB。
- 显示画面时，准备好的视频要以约 5.5 Mbps 串流，而实测网络只有约 8.5 Mbps。

同一天提出的流畅版能把码率降到约 1.9 Mbps，代价是服务器要转码，画面也变小。

用户面前的电脑上往往就有同一个视频，因为剧集本来就是从那里导入的。从那里播放，画面完全不经过网络，跳转和读磁盘一样快，
画质也是完整的。2026-10-13 提出的问题是：页面能不能播放这样的文件，又不把它放进媒体库。

在本地的 dsh 上这没有区别：服务器就是这台电脑，本来就从磁盘读文件。好处只在远程的 dsh 上。

## Decision

**视频舞台上加「用本地文件播放」：用户从自己的磁盘选出这一集的视频，页面就用它代替服务器上的那份播放这一段，
不上传。**

- **文件不离开浏览器。** 文件用文件选择框打开（或者拖到舞台上），通过对象 URL（`URL.createObjectURL`）播放。
  它不上传、不导入，也不写到任何地方，服务端完全不知道它的存在。把视频拖到舞台上表示「播放这个」，拖到首页仍然表示「导入」，
  和以前一样。
- **共用同一条时间线。** 本地文件经 `playSource` 成为媒体元素的来源，优先于服务器上的视频，会话不变。
  所以位置、循环、语速、字幕、收藏的句子、复习和五步法，都和播放服务器上的视频时一样。隐藏画面时仍然播放音频文件；
  有本地文件时这样做省不了什么，但规则可以只有一条。
- **必须是同一个视频。**
  - 本地文件的时长先和服务器上那份视频的时长比较（状态路由已经报告了这个值）；那份视频没探测过时，就和音频文件的时长比较。
  - 相差一秒以内就当作同一个文件，服务器视频与音频之间原有的时长检查照样适用。
  - 时长不同时，显示现有的「字幕可能对不上」提示并给出差值，但照样播放，因为同一集的另一个剪辑版本仍然值得看。
- **必须是浏览器能播放的文件。** 浏览器里没有 `ffmpeg`，所以各处都能播放的格式是 `mp4`（H.264 加 AAC）。
  浏览器解码不了的文件，经现有的「无法解码」路径退回服务器上的来源，并提示改用 `mp4`。源 `mkv` 在 Chromium 里可能有画面没声音（DTS、AC-3），
  页面只事先提示这一点（见 Settled details）。
- **在本次页面会话里有效，浏览器允许的话保留更久。** 对象 URL 随页面关闭而失效。在支持 File System Access API 的浏览器上
  （HTTPS 上的 Chromium，线上站点正是这种情况），文件句柄按段存进 IndexedDB，再次打开这一段时只需授权一次读取，
  不必重新选文件。其他浏览器上，用户再选一次。这些都不发给服务端，所以和设置一样按设备保存。
- **一眼就能看出来。** 舞台在本地画面上加「本地文件」标签，并提供停用的办法，用户不会搞不清正在播放哪个文件。

## Alternatives considered

- **把文件上传进媒体库。** 这就是现有的导入。上传要花一次时间，之后每次播放还要串流，而串流正是要解决的问题。
- **本地画面静音播放，声音用服务器上的音频。** 能应付声音是 DTS 的源文件，但这需要两个媒体元素保持同步，视频那篇 note 已经否决了这种做法：
  每次跳转、改语速和循环都要做两遍，两个元素之间还会慢慢错开。
- **把服务器上的视频一次性下载到浏览器存储（OPFS），之后从那里播放。** 不需要本地副本，但问题有三个：
  - 941 MB 以 1 MB/s 下载约需 15 分钟。
  - 浏览器对这么大的存储有上限，也可能把它清掉。
  - v0.9.3 加的缓存校验头已经让 HTTP 缓存尽量多地保留内容。

  如果没有本地副本的用户提出需要，这仍是一个选项。
- **合并进流畅版那篇 note。** 两者针对的是同一个抱怨，但没有共用的代码：流畅版是服务端上改写文件的任务，这个是只在前端起作用的来源。
  分开写，各自可以单独实现或放弃，而且两者能同时使用：有文件的用户在本地播放，没有的用户用流畅版。

## Settled details

提出时有两个问题还没定，2026-10-13 动手之前定了下来：

- **浏览器播放不了的格式，只提示，不检测。** 选择文件的地方写明：`mp4`（H.264 加 AAC）各处都能播放，`mkv` 常常没有声音；声音方面不再做别的处理。
  检测音轨缺失（非标准的 `webkitAudioDecodedByteCount`）或者读取容器的轨道列表，是为一个用户换个 `mp4` 一分钟就能解决的情况写代码。
  浏览器完全解码不了的文件，则退回服务器上的来源，提示改用 `mp4`，并且忘掉这个文件，因为下次它同样解码不了。
- **参照时长可以退回到音频文件。** 先和服务器上那份视频探测到的时长比较。服务端从没探测过时（视频从没准备过），改用这一段的音频文件，
  因为字幕本来就是对着它打的时间。这样，任何有视频文件的段都能用本地画面，不管视频准备过没有。两个时长都不知道时，照样播放，不给提示。

动手时又定了这些：

- **本地文件排在服务器视频的所有状态之前**，包括正在执行的任务和失败的任务。只要这一段有视频文件，就提供这个选项，入口有两处：
  画面一角的小按钮，以及每张卡片的最后一行。隐藏画面时，规则和服务器视频的一样：播放音频文件；没有音频文件的段播放本地文件，因为那是唯一的声音来源。
- **时长由一个用完就丢的元素读取**，不用页面上唯一的那个媒体元素，所以那个元素只加载文件一次。读不出时长的容器（部分 `mkv`）
  不给提示，免得给出错误的提示。
- **两个警告，一条规则。** 本地文件和参照相差一秒以内就是同一个文件，这时服务器视频与音频之间的长度警告照样适用。
  不是同一个文件时，改为显示现有的警告，给出和参照的差值（本地文件更长时为正）。
- **只有浏览器支持 `showOpenFilePicker` 时才记住选择。**
  - 句柄按段存在 IndexedDB 里，只在这台设备上。
  - 再次打开这一段时，显示带文件名的「继续用本地文件」，因为申请读取权限需要点击一次。
  - 「忘记」会删掉记住的句柄，「停用」不会（停用不代表这个文件有问题）。文件已经不在的句柄，先告知用户再丢弃。
  - 其他浏览器用普通的文件输入框，用户每次页面会话都要重新选一次。
  - IndexedDB 的每次调用都允许失败，失败时什么也不记。
- **对象 URL 的寿命和文件的使用时间一样长。** 文件被替换或停用时、换段时（记住的句柄会再次提供这个文件）、页面关闭时，都会撤销它。
- **本地文件播放时先不弹「视频准备好了」。** 这条提示说的是服务器上的视频，而那时播放的不是它。
- **视频拖到练习页的舞台上就是选择它，不会触发别的操作。** 只接收视频文件，拖进来的其他东西都被忽略（浏览器也不会打开它们），
  这次拖放也不会交给导入，导入仍然只在首页。
