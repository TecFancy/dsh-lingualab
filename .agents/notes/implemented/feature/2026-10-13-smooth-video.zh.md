# Agent Note: 给慢线路准备流畅版视频

Status: implemented

## Problem

准备好的视频原样保留画面。线上服务器唯一的那一集，画面是 720p 的 H.264，约 5.3 Mbps，所以准备出的 `mp4`
23 分钟有 941 MB，播放时约 5.5 Mbps。2026-10-13 实测服务器线路约 8.5 Mbps（1 MB/s），往返约 20 ms，
瓶颈在带宽，不在延迟：

- 播放只有约 1.5 倍余量，画面码率一冲高，或者同时有别的请求，就会卡；线路低于 5.5 Mbps 的读者根本没法连续播完；
- 跳到没缓冲的位置，要等 4 到 8 秒画面才重新动起来；
- 文件开头的索引有 1.4 MB，光是拿到时长就要一秒多。

v0.9.3 去掉了用不着画面的情形（隐藏画面时改放音频文件），也让浏览器能复用已经下过的数据。可只要看画面，
仍然需要 5.5 Mbps。

视频那篇 note 把重新编码放到一边，理由是重新编码 23 分钟的画面比看一遍还慢。那是在开发机上量的。2026-10-13
在服务器上，`libx264` 用 `veryfast`、码率上限 1.8 Mbps，转这一集的一分钟，速度是实时的 1.53 倍（每秒 37 帧），
结果平均 1777 kb/s。整集约需 15 分钟，连声音约 330 MB。这个代价值得提供出来，但还不到每个视频都转一遍的程度。

## Decision

**新增第二种准备方式「准备流畅版」，为串流重新编码画面。** 它按一集或一段手动启动，准备好之后取代原尺寸的准备文件。

- **写出什么。** H.264（`libx264`，`veryfast`，CRF 23，码率上限 1.8 Mbps，缓冲 3.6 Mbit），8 位 4:2:0，
  高度不超过 720 行（更小的画面保持原尺寸），不管帧率多少都每 2 秒一个关键帧，声音是 128 kb/s 的立体声 AAC，
  索引放在开头（`+faststart`）。每 2 秒一个关键帧，意味着一次跳转最多多下约半兆不播放的数据；源文件的关键帧平均约
  4 秒一个。
- **手动启动。** 页面能显示画面的视频，在画面的角上多一个「准备流畅版」操作，旁边写着预计体积和耗时。它走现有的一次一个的
  任务队列，进度和「取消」与准备视频相同；任务失败或被取消，当前文件照常播放。普通的准备保持不变：一分钟的换封装，
  不重新编码。
- **是取代，不是并存。** 结果写成 `<剧集>/.lingualab/<词干>.smooth.mp4`（和现在一样先写 `.part`）。它到位之后，
  缓存里原尺寸的 `<词干>.mp4` 就删掉，所以一集占 330 MB 磁盘而不是 941 MB，不会两份都占。能直接播放的源文件是读者自己的文件，
  从不改动，只是优先用流畅版。状态路由按流畅版、准备版、直接播放的顺序挑选，并说明是哪一种（`via: 'smooth'`），
  页面可以据此标注。
- **不拖慢宿主。** `ffmpeg` 进程以较低的优先级启动（`os.setPriority`，10，在 Linux 和 Windows 上都管用），
  线程数比机器的核数少一个，所以转码期间 dsh 的页面照样流畅。机器忙时转码会慢一些，一集只跑一次的任务担得起。
- **播放器不用改。** 任务完成后，状态路由返回的 URL 变了，页面本来就会在同一个会话里换源并保留位置。v0.9.3
  加的缓存校验头会告诉浏览器这些字节是新的。

## Alternatives considered

- **准备视频时一律重新编码，或者用配置开关控制。** 省一次点击，但每个视频都要等 15 分钟而不是一分钟，线路快的读者也白白牺牲了画质。
  按集、按需准备，和视频那篇 note 处理准备的方式一致。
- **两份都留，加一个画质切换。** 线路快的读者可以保留完整画面，但每集要占约 1.3 GB，还多一个控件和一项设置。720p
  的流畅版看场景、跟对白已经够用，而五步法用画面就是为了这个。
- **自适应串流（多档码率的 HLS 或 DASH）。** 能按线路自动选画质，但需要切片工具、清单路由，以及宿主模块表里没有的播放器库，
  几档码率也比一档更费转码和磁盘。对一次只有一个读者的插件来说，机制太重。
- **更低的分辨率，比如 540p、1 Mbps。** 更小，但实测 720p、1.8 Mbps 在这条线路上已经有约 4.5 倍余量，而且
  720p 下画面里的文字（招牌、手机屏幕）还看得清。
- **VP9 或 AV1。** 同样画质小约三分之一，但用 CPU 编码要慢好几倍，15 分钟会变成一小时以上。
- **给媒体挂 CDN。** 能提升线路本身，对所有文件都有帮助，但那是部署层面的选择，不在这个插件里。用服务器的人多了，仍然值得做。
- **为改回原画质单开一条路由。** 准备路由本来就收一个 mode 并回状态，而改回去就是「按原来的样子准备」，所以只是多一个 mode，
  不值得再多第四条路由，连同它的命名记录和守卫。
- **原尺寸的准备文件和流畅版并排留着。** 改回去能瞬间完成，但那正是流畅版要省掉的 941 MB，而改回去只花一分钟的换封装。

## Settled details

提出时有两个问题没定，主人在 2026-10-14 动手之前定了：

- **在「只能准备声音」的卡片上也提供流畅版。** 重新编码能让 `ffmpeg` 解得开的任何画面都变得可播放，包括 HEVC、MPEG-4 Part 2
  和 10 位 H.264，它们本来只能准备声音。所以这些视频的卡片上也有「准备流畅版」，同一个任务就能把它们变成能放的视频。
  这把功能扩展到了慢线路之外；它在纯函数的规划器里（`planSmooth`）按同一次探测来规划，对任何有画面有声音的文件都成立，
  并在那里有单元测试。
- **「改回原画质」是一个操作。** 远程的读者没法手动删服务器上的文件，没有它，流畅版就是一扇单向门。它放在正在播放的流畅版画面上，
  删掉 `<词干>.smooth.mp4`，再通过同一个任务队列把视频准备成原来的样子（一分钟的换封装）。对只可能是声音的源文件
  （画面浏览器解不了），改回去只是删除，回到只有声音的状态。

实现时做的决定：

- **流畅版的任务不把画面拿走。** 它是唯一一个在画面正放着时运行的任务，所以运行期间状态仍是 `playable`（或 `sound-ready`），
  带着 URL，只多了 `progress` 和 `jobKind: 'smooth'`；画面的角上显示百分比和「取消」。没有东西可放的状态（没准备、只有声音、
  有音频文件但画面解不了）变成 `preparing`，由卡片显示进度，和其他任务一样。页面靠 `progress` 而不是靠状态判断有没有任务在跑，
  只在正在放的文件真的换了的时候才说「流畅版准备好了」，所以被取消或失败的流畅版什么也不说。
- **失败的流畅版由 smooth 字段来说。** 它不变成 `failed` 状态，那会盖住正在放的画面；它是 `smooth.error`，显示在控件下面和卡片上，
  操作也会再次提供。
- **在哪里提供。** 正在放的画面的角上，以及准备卡片的底部（`mkv` 最常见，而且流畅版比它所取代的换封装文件更小）、
  只有声音的卡片、声音已取出的卡片，还有「放不了」的卡片（段有自己的音频文件、画面浏览器解不了时就是它）。失败、ffmpeg 和进度卡片上不提供。
  没有 `ffmpeg` 和 `ffprobe`、文件没有声音或没有画面、这一段有任务在跑、流畅版已经存在时，都不提供。读者自己的本地文件在放，
  或者画面被隐藏时，角上保持安静。别的段在跑任务，就是惯常的 `busy` 拒绝，显示在控件下面。
- **预计数字就用提案里的，不搞花样。** 体积约 1.9 Mbps（画面加声音），耗时是实时的 1.5 倍，都从探测到的时长算，所以由 host 计算，页面只负责措辞
  （「约 315 MB，约 16 分钟（估计）」，时间取整分钟，不到一分钟就这么写）。进度卡片上的剩余时间，两分钟以上改用分钟。
- **优先级和线程。** `os.setPriority(pid, 10)` 在启动进程后立刻调用，只对流畅版的任务，被拒绝时吞掉（任务照常优先级运行，只是慢一点）。
  线程数是 `os.availableParallelism()` 减一，至少一个，用 `-threads` 传下去。两者都经过一个小小的、注入进来的宿主描述，
  所以任务的测试从不碰真进程，测试里的假进程除非测试给了就没有进程号。
- **`ffmpeg` 的参数，拿真的验证过。** 高度上限是 `scale=-2:min(720\,ih)`（逗号要转义，否则滤镜图把它读成滤镜的结束；`-2` 让宽度保持偶数），
  像素格式强制成 `yuv420p`，关键帧来自 `-force_key_frames expr:gte(t,n_forced*2)`。装了真 ffmpeg 的机器上，测试确认 1080 行变成 720 行，
  240 行仍是 240 行，关键帧在 25 和 60 帧每秒下都落在 0、2、4 秒。流畅版的声音是 128 kb/s，准备版的声音仍是 160 kb/s。
- **取代发生在任务里，改名之后。** `<词干>.smooth.mp4` 到位后才删原尺寸的 `<词干>.mp4`；浏览器还开着的文件可能删不掉（Windows），
  这没有害处，因为优先用流畅版。只有声音的 `<词干>.m4a` 不动，这正是改回去能让只有声音的源文件回到原状态的原因。
  比源文件旧的流畅版不算数，和其他缓存文件一样。
- **改回去是准备路由的一个 mode**（`mode: 'original'`）。没有流畅版时什么也不做。有任务在跑时拒绝并且不删任何东西，
  因为那个任务可能正在写将来取代它的文件。否则删掉流畅版，需要换封装的源文件通过队列开始那个任务；能直接播放的，
  或者画面浏览器解不了的，不需要更多了。已经存在流畅版时再要流畅版，会被拒绝。
- **一次一个仍然是「忙」，不是排队等候。** 提案里写的是队列；现有的执行器对第二个任务回答 `busy`，流畅版照做，
  不为只有它会用的队列另起炉灶。
- **只有声音的卡片不再说重新编码比看完一集还慢。** 那曾是只取声音的理由；现在卡片在旁边提供流畅版。失败卡片上的「重试」，
  遇到失败的是只取声音的任务时也改为再要一次声音；以前它要的是画面，而 host 对这样的文件会拒绝。
- **一个已知的边角。** 词干本身以 `.smooth` 结尾的段，会和没有这个结尾的那一段的流畅版文件重名。这很少见，
  为它让所有人用更长的扩展名不值得。
