# Agent Note: 继续用文件存数据，并让笔记的保存更安全

Status: implemented

## Problem

页面保存的东西都是素材库里的普通文件：

- 每集一个 `notes.md`，记收藏的句子（备注、单词和评级）。
- 媒体库根目录的 `.lingualab-progress.json`，记每集或每段听到哪里，以及五步的勾选。
- 字幕文件本身，调整时间的横栏会把改动写回去。

2026-10-12 提出的问题是：要不要用一个 SQLite 数据库替换这些文件。一个应用一旦要存记录、查记录、频繁写记录，通常的答案就是数据库。

评估的结论是，SQLite 在这里不值它的代价，但评估也发现了 `notes.md` 写入方式上的两个真实弱点。两个结论当天都被采纳：
文件保留，「Decision」一节里的两处修复也在当天做完。这篇 note 保留对 SQLite 的评估，以后再遇到这个问题时不用从头想一遍。

## Assessment

SQLite 能带来的：

- **跨整个库的查询。** 现在整个库的复习队列，是把每一集的 `notes.md` 都读出来再解析得到的（`src/host/review.ts`）。
  如果有一张收藏句子的表，「所有还在练的句子」就是一条查询；每句的历史（每次评级和日期，这是间隔重复的基础）也很容易加上。
- **原子、并发安全的写入。** `notes.md` 用 `writeFileSync` 原地重写（`src/host/notes.ts`），写到一半崩溃，可能留下一个被截断的文件；
  两个标签页保存同一集，后保存的会覆盖先保存的。SQLite 的事务和 WAL 模式能同时解决这两个问题。
- **容易扩展的结构。** 新字段（复习日期、来源段、标签）只是加一列，不用去改一种用竖线分隔、还得让旧代码读得懂的行格式。

它的代价：

- **agent 读不到原来的数据。** `notes.md` 不只是存储。方法里有两步（次日复习和周日复习）在对话里进行，agent 读的就是这个文件；
  人也会打开它浏览，或者手动修改收藏。换成数据库后，要提供导出功能，或者给 agent 一个查询工具，这两类读者才能拿回现在拥有的东西；
  而导出的文件又是同一份数据的第二个副本，需要保持同步。
- **文件不再方便随身带走。** 现在一个剧集文件夹是自包含的：拷到另一台机器上，笔记和音频一起过去。整个库用一个数据库，会把两者分开；
  每个剧集文件夹用一个数据库，又会失去大部分查询上的好处。
- **服务端（host）多一个运行时依赖。** `lib/index.js` 是提交进仓库的单文件产物，不含原生模块。`better-sqlite3` 是原生模块，
  要针对 harness 运行的那个 Node 版本编译；内置的 `node:sqlite` 不用编译，但会把插件绑定在较新的 Node 版本上，
  而且它的 API 有很长一段时间都标着实验性。
- **数据量很小。** 一集收藏几十句，一季几百句，把每个 `notes.md` 都解析一遍只要几毫秒。目前没有哪个功能是因为用文件而变慢的。

## Decision

**markdown 和 JSON 文件继续作为唯一的数据来源，不用 SQLite。** 评估发现的两个弱点确实存在，都在文件这一侧修复：

- **笔记的写入是原子的。** `notes.md` 改成和进度文件（`src/host/progress.ts`）一样的写法：先写到旁边的临时文件，再改名覆盖旧文件。
  这样即使崩溃，留下的也只会是旧文件或新文件，不会是写了一半的文件。
- **基于过时内容的保存会被拒绝。** 页面记下它读到的 `notes.md` 内容的哈希，每次保存都带上，做法和调整时间的横栏对字幕文件的处理一样
  （`src/host/timing.ts`）。如果文件在这期间被改过（另一个标签页、手动修改、agent），服务端返回「内容已过时」，不覆盖文件；
  页面重新读取笔记，并说明原因。保存成功时，返回结果里带上新的哈希，所以同一个标签页连续保存不受影响。

每处修复都有测试，放在 `src/host/notes.test.ts` 和 `src/host/routes.test.ts`：写到一半失败时，旧文件完好无损；带着旧哈希的保存不会改动更新过的文件。

## Alternatives considered

- **只用 SQLite 存储。** 能拿到查询和事务的全部好处，代价是 agent 读不到数据、不能手动修改、不能按文件夹带走，还要加一个原生或绑定版本的依赖。
  只要 agent 还直接读 `notes.md`，就不采用。
- **以 SQLite 为主，每次写入都导出一份 `notes.md`。** 两类读者都照顾到了，但数据有两份；人手动修改 `notes.md` 时，改的正是会被覆盖的那一份。
- **把 SQLite 当作从文件生成的索引。** 启动时或文件变化时从各个 `notes.md` 重建，从不直接写入，删掉也没关系。
  这样 agent 照样能读文件，文件夹也照样能带走，所以如果哪天整个库的查询真的变慢了，就该采用这种形式。现在还用不着。
- **每集用一个 JSON 文件代替 markdown。** 比竖线格式更好解析、更好扩展，但人和 agent 读起来都更费劲，而选 markdown 本来就是为了好读。
- **保留文件，什么也不改。** 文件被截断、两个标签页互相覆盖的风险都还在。

## When to revisit

- 加了间隔重复，需要记下每一次复习的历史，一行已经放不下。
- 库变大了，为整库复习读一遍所有 `notes.md` 明显变慢（先测量，别凭感觉）。
- agent 有了查询页面数据的工具，不再需要读 `notes.md`。
- 经常有不止一台设备写同一集，按文件合并成了问题。
