# Agent Note: 客户端半边用 FSD，但没有 app 层

Status: implemented

## Problem

这一页小到用一个长组件就能写完，host 半边相比之下也是平的。隔壁 `fsd-react` 是一套完整的
应用脚手架：路由、组件库、设计令牌管线，还有一个产出 Web 应用的构建。插件产物不是这些东西，
它是一个经典脚本，向宿主的模块表注册自己，所以照搬那套脚手架等于引进一套用不上的构建，和一批
宿主本来就提供的依赖。

与此同时，这一页要装的东西在变多。写第一行代码之前，视频和听写就已经在计划里了。

## Decision

客户端半边按 FSD 分层组织，有 `shared`、`entities`、`features`、`widgets`、`pages` 五层，
没有 `app` 层。注册、Provider 和路由留给宿主，所以 `index.tsx` 待在被分析目录的根上，只做一件事：
把中栏那一页接到宿主的 `main` 插槽上。Steiger 在 `src/client` 上执行分层规则，页面负责
组合各个 feature，feature 之间不互相伸手。

## Alternatives considered

- **一个长组件。** 第一版最省事，也意味着以后加视频和听写都在改同一个文件。否掉的理由就是这一页
  存在的理由：它注定要长过「听」这一件事。
- **fork `fsd-react` 再加一个插件构建出口。** 架构和整套检查都保住了，代价是两套构建，外加一个
  产物里用不上的路由和组件库。否掉：那个仓库真正可复用部分是它的规矩，规矩不需要脚手架就能搬。
- **照抄废弃复读机的目录结构。** 它也是 FSD，但它的切片穿过 `entities/subtitle` 这个只有类型的
  实体导入，store 是单例并被 widget 直接接线。只学形状不学接线，会得到一个两头不靠的结构。

## Consequences

加一个新能力就要新建一个切片并给它写公开入口，比往一个组件里加文件麻烦。换来的是分层由检查守着，
而不是靠记忆；每一个跨切片的导入都走一个一眼能读完的 barrel。
