# Agent Note: 前端用 FSD 分层，但没有 app 层

Status: implemented

## Problem

这个面板不大，写成一个长组件也装得下；服务端（host）的代码则完全没有分层。隔壁的 `fsd-react`
是一套完整的应用脚手架，有路由、组件库、设计令牌管线，还有一个产出 Web 应用的构建。插件产物不是这些东西，
它只是一个经典脚本，加载后向宿主的模块表注册自己。照搬那套脚手架，就会引进一套用不上的构建，
外加一批宿主本来就提供的依赖。

另一方面，这一页要承载的内容在变多。写第一行代码之前，视频和听写就已经在计划里了。

## Decision

前端（client）按 FSD 分层组织，有 `shared`、`entities`、`features`、`widgets`、`pages` 五层，
没有 `app` 层。注册、Provider 和路由都由宿主负责，所以 `index.tsx` 放在被分析目录的根上，只做一件事：
把这一页注册到宿主的 `main` 插槽上。

- Steiger 在 `src/client` 上检查分层规则。
- 页面负责组合各个 feature。
- feature 之间不互相导入。

## Alternatives considered

- **写成一个长组件。** 第一版最省事，但以后加视频、加听写都要改同一个文件。不采用，理由正是这个面板存在的理由：
  它注定不会只做「听」这一件事。
- **fork `fsd-react`，再加一个产出插件的构建目标。** 架构和整套检查都能保住，代价是两套构建，
  外加插件产物用不上的路由和组件库。不采用：那个仓库真正能复用的是它的规矩，规矩不需要脚手架也能搬过来。
- **照抄已废弃的复读机应用的目录结构。** 它也是 FSD，但它的切片都经过 `entities/subtitle` 导入，
  而这个实体里只有类型；它的 store 是单例，由 widget 直接接线。只学目录形状、不学接线方式，结果会是一个不伦不类的结构。

## Consequences

加一个新能力，就要新建一个切片并给它写公开入口，比往一个组件里加文件麻烦。换来的好处是：

- 分层关系由检查守住，不靠记忆。
- 每一处跨切片的导入都经过一个 barrel，审阅的人一行就能读完。
